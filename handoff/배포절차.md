# 과제용 배포 절차

## 1. 운영 환경과 분리
이 폴더는 과제용 전용 저장소로 올린다. 운영 저장소에 PR 또는 push하지 않는다.
기존 Supabase 프로젝트에 설치 SQL을 실행하지 않는다. 새 빈 프로젝트만 사용한다.
운영 service-role 키, OAuth secret, 메일·OneDrive 수집 토큰을 복사하지 않는다.

## 2. 데이터베이스
신규 프로젝트를 생성한 후 database/ASSIGNMENT-DATABASE.md의 설치 절차를 따른다.
설치 번들은 빈 데이터베이스 여부를 검사하고, 기존 업무 스키마가 있으면 중단한다.
개별 사용자는 인증 뒤 ensure_assignment_workspace RPC로 전용 공간을 만든다.
샘플 화면(?demo=1)은 서버 데이터를 읽고 쓰지 않는 합성 시연이며 계정별 저장 시험이 아니다.

## 3. 프런트엔드 설정
`.env.example`을 `.env.local`로 복사하고 신규 프로젝트 URL/ref/publishable key를 입력한다.
VITE_ 변수는 브라우저에 공개되므로 secret/service-role 값을 넣지 않는다.
기존 프로젝트 ref와 주소를 넣으면 연결을 거부한다.

```sh
npm ci --ignore-scripts
npm test
npm run check:isolation
npm run build
npm run dev
```

일반 build는 미설정 안내 화면도 만든다. 실제 배포용 검사는 셸/CI에 설정된 환경변수로 실행한다.

```sh
npm run build:deploy
```

## 4. 로그인
신규 Supabase Auth에서 배포 HTTPS 주소를 Site URL과 정확한 Redirect URL로 등록한다.
이메일 확인을 켜고 실제 인증메일 수신을 테스트한다. 기본 메일 제한이 있으면 승인된 SMTP를 설정한다.
Microsoft 로그인은 신규 애플리케이션 설정과 조직 정책 확인 후 `azure`, Google은 별도 설정 후 `google`을 VITE_ASSIGNMENT_OAUTH_PROVIDERS에 넣는다.
Microsoft 회사 전용으로 제한하려면 조직 tenant 및 사용자 정책을 확인한다. 버튼 표시만으로 직원 전용 인증이 보장되지는 않는다.

## 5. 배포
별도 저장소의 verify workflow는 테스트와 빌드를 수행한다.
배포 workflow는 수동 실행부터 시작한다. 변수 이름은 workflow에 명시되어 있다.
GitHub Pages 사용 가능 여부는 계정 플랜/비공개 저장소 정책을 확인한다. 정적 docs 디렉터리는 Cloudflare Pages 등에도 배포 가능하다.
MCP는 별도 HTTPS 서버가 필요하다. 정적 HTML/GitHub Pages만으로 MCP 서버는 실행되지 않는다.
개인 AI 연결 설정은 bridge/README.md의 OAuth 및 환경변수 설정을 따른다.

## 6. 배포 후 검증
- 미로그인 데이터 접근 차단
- 신규 사용자 A/B의 서로 다른 작업공간
- A의 업무/대화가 B에게 읽히지 않음
- 대화 저장·다시 조회·중복 전송 방지
- AI가 완료한 작업을 원본 재수집이 되돌리지 않음
- 로그아웃/재접속 후 기록 유지
- 비밀번호 재설정, OAuth 실패/취소/재시도
- 375/768/1280px 화면 및 원문 링크
- 과제 변경 중 운영 코드와 DB에 쓰기 요청 없음

## 7. 프런트엔드·MCP 한 서버 배포
Dockerfile은 Node 22에서 프런트엔드를 빌드하고 HTTPS 플랫폼 뒤에서 업무보드와 /mcp를 함께 제공한다. VITE_ 공개값은 빌드 인자, ASSIGNMENT_ 서버값은 런타임 환경변수로 제공한다. HTTPS 인증서와 도메인은 배포 플랫폼에서 설정한다. 컨테이너 자체는 HTTP 8788을 사용한다. 실제 Docker 이미지 빌드는 이 작업 환경에서 검증하지 않았다.
